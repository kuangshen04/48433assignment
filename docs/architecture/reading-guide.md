# 阅读方式

这套文档没有把 Q&A 拆散后逐段复制，而是按**问题类型分权**：为什么这样定、现在怎么设计、一次操作怎么穿过系统，各由一个地方负责。

## 权威划分

不存在"唯一事实源文件"，只有"每个问题只有一个权威"：

| 文档 | 回答的问题 | 权威范围 | 不该出现 |
|---|---|---|---|
| [完整决策日志](/decisions/log) | 为什么这样定、否决了什么、接受什么代价 | 决策与理由 | 字段表、方法签名、状态机细节 |
| [决策目录](/decisions/catalog) | 决定了什么（编号 + 状态） | 索引 | 论证 |
| [系统视图](/systems/traceability-core) | 现在怎么设计 | **行为、接口、不变量** | 长篇 trade-off |
| [跨系统流程](/flows/event-acceptance) | 一次操作怎么穿过系统 | 跨系统契约验证 | 设计理由 |
| [待办清单](/decisions/backlog) | 还剩什么 | 计划 | 已完成的论证 |
| [产品与运营参数](/decisions/open-items) | C1–C3 关成了什么配置 | 参考配置与验收 | 架构决策 |

**冲突时的规则：行为以系统页为准，理由以决策日志为准；两者冲突即视为 bug。**

判断一段内容该放哪，用两个问题：

1. 它会因为**实现变了**而改，还是只会因为**理由变了**而改？前者是设计，后者是决策。
2. 删掉它，决定还能不能说清"我们划了哪条线"？能 → 它只是说明；不能 → 它其实是决定。

结构性决定（例如"non-collapsing 只在唯一查询入口强制"、"地板编译后冻结"）读起来像实现细节，但它们是边界本身，必须留在决策日志里。

## 信息维护规则

- 新的重大取舍先进入[完整决策日志](/decisions/log)，并获得新的或现有决策编号。
- 决策改变后，再更新受影响的系统页和流程页；**设计细节只写在系统页，不在日志里复述**。
- 系统页不重复长篇 trade-off，只说明当前契约及其来源。
- 同一规则只指定一个主要负责系统；其他系统通过接口或只读投影使用它。
- C1–C3 已关闭为 reference deployment；产品名是参考实现，不是架构依赖。
