# C4 视图 · 上下文与部署

这两张是"系统级"的图：context 说明系统边界和外部依赖，deployment 说明这些东西实际跑在谁的账户里。图内英文，说明中文。

职责与不变量的权威仍在系统页；本页只解释图。

## System context

<img src="/diagrams/c4-context.svg" alt="C4 system context: users, external systems and the traceability system">

四句话：

1. **黑框里只有一个系统。** 参与方的 ERP/WMS、监管方的规则引擎、外部归档和 KMS 都在框外——它们各自的职责与失败语义见对应系统页。
2. **IoT 设备不直接连平台。** 传感器、秤、扫码枪先进入参与方的业务系统或网关，再由业务系统发布 EPCIS 事件。这一条决定了平台不需要做设备管理，也决定了原始遥测留在参与方一侧。
3. **身份有两条独立的线。** 人员认证来自外部 IdP（`OIDC`）；组织的法律身份在 onboarding 时经企业登记库核验。前者管"谁在操作"，后者管"这个组织是否存在"——两者都不是平台自己发证的。
4. **三个外部依赖承担了"平台之外的证明"**：外部归档签 `ArchiveAck`、联盟 KMS 持有密钥、公链保存 Merkle 根。它们在图上被画在系统边界之外，正是因为它们的价值来自"不在平台的账户里"。

## Deployment

<img src="/diagrams/c4-deployment.svg" alt="C4 deployment view: cloud accounts, regions and runtime nodes">

要点：

1. **四个控制域，四组账户。** 平台账户、监管方账户、联盟/受托方账户各自独立；公链是外部基础设施。这张图是 B1（平台不被完全信任）在部署层的落地——如果四个域被合进一个账户，前面所有证明都退化成平台自证。
2. **单区域起步，但副本跨故障域。** 应用与数据库在一个 Australian region；归档与 KMS 在受托方账户、跨故障域保存。多活不在首版范围内，触发条件写在部署页。
3. **容器与托管服务分开表达。** 应用与 worker 是容器实例（同一镜像的不同角色），数据库、对象存储、KMS 是托管服务；没有自管集群，也没有自建 CA。
4. **钱包只有一个进程持有。** `Batch Builder & Relayer` 单独部署，是唯一接触链上私钥的组件——它被画成一个隔离的 worker，而不是应用的一部分。

## 这两张图刻意不定的事

部署图里的托管产品**没有写具体名字**：数据库、容器运行时、对象存储、KMS 产品都属于 C1–C3 的产品级选型，仍在[待定事项](/decisions/open-items)里。图上给的是逻辑位置与控制域归属，这两件事定下来之后，换任何一家供应商都不改变结构。

同理，区域只画了一个 primary region；多区域、灾备演练与成本数字属于 reference deployment 的正文内容，不在图里。
